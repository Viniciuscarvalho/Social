## 🎨 Padrões Estabelecidos

### Estrutura de Feature

```
Feature/
├── [Name]Feature.swift      → State, Action, Reducer
├── Views/
│   ├── [Name]View.swift     → View principal
│   ├── [Name]Cell.swift     → Células e subviews
│   └── Components/          → Componentes específicos
└── README.md (opcional)
```

### Separação de Responsabilidades

#### Feature (Reducer)
- ✅ State management
- ✅ Lógica de negócio
- ✅ Chamadas de API (via clients)
- ✅ Error handling
- ❌ NÃO contém código SwiftUI

#### Views
- ✅ Renderização visual
- ✅ Layout e UI
- ✅ Uso de componentes DS
- ❌ NÃO contém lógica de negócio

### Integração com Outras Camadas

```
View → Feature → Client → NetworkService → API
                    ↓           ↓
                 Domain ← Data (DTOs + Mappers)
                    ↓
              DesignSystem
```

## 🔧 Convenções Estabelecidas

### State
```swift
@ObservableState
public struct State: Equatable {
  // Domain Data
  public var data: [Model] = []
  
  // UI State
  public var isLoading = false
  public var errorMessage: String?
  
  // Navigation State
  public var showingDetail = false
  
  // Derived State
  public var hasData: Bool {
    !data.isEmpty
  }
}
```

### Actions
```swift
public enum Action: Equatable {
  // Lifecycle
  case onAppear
  case onDisappear
  
  // Data Loading
  case loadData
  case dataResponse(Result<[Model], NetworkError>)
  
  // User Interactions
  case itemTapped(UUID)
  
  // Navigation
  case setShowingDetail(Bool)
  
  // Error Handling
  case dismissError
}
```

### Views com Design System
```swift
// ✅ BOM - Usando componentes DS
Button("Salvar") {
  store.send(.saveButtonTapped)
}
.dsPrimaryButton()

DSCard {

.padding()
.background(Color.blue)

```

## 📖 Decisões Técnicas

### 1. Abordagem Incremental
**Decisão**: Estabelecer padrões e documentação primeiro, migrar Features incrementalmente depois (Task 10.0).

**Razão**:
- Task 5.0 é M/L (Medium/Large) mas migrar todas as Features seria unrealistic
- Migração incremental é mais segura e controlada
- Permite validar padrões antes de migração em massa
- Task 10.0 específica para migração incremental

### 2. Derived State com Computed Properties
**Decisão**: Preferir computed properties para estado derivado ao invés de duplicar state.

**Razão**:
- Evita desincronização de estado
- Reduz bugs
- Código mais limpo e manutenível
- Performance adequada (computed properties são rápidas)

### 3. Design System Obrigatório
**Decisão**: Views DEVEM usar componentes do Design System, não criar componentes customizados básicos.

**Razão**:
- Consistência visual
- Reduz código duplicado
- Facilita manutenção
- Melhora acessibilidade

### 4. Types do Domain, não DTOs
**Decisão**: Features devem usar apenas tipos do Domain, nunca DTOs diretamente.

**Razão**:
- Separação de camadas
- Features não dependem de detalhes de API
- Facilita testes
- Permite trocar implementação de Data sem afetar Presentation

### 5. Result Types para Error Handling
**Decisão**: Usar `Result<Success, NetworkError>` para responses de API.

**Razão**:
- Type-safe error handling
- Força tratamento explícito de erros
- Facilita debugging
- Padrão do TCA

## 🎓 Aprendizados e Guidelines

### Boas Práticas Documentadas

1. **Sempre use @ObservableState**: Necessário para observation do TCA
2. **Actions devem ser Equatable**: Permite testabilidade
3. **Organize Actions por categoria**: Lifecycle, Data, UI, Navigation
4. **Use computed properties para derived state**: Evita duplicação
5. **Mova lógica da View para Reducer**: Views devem ser "dumb"
6. **Use componentes DS, não reimplemente**: Consistência e DRY
7. **Proper error handling**: Sempre use Result types
8. **Teste todos os fluxos**: Loading, Success, Error, Empty

### Anti-Patterns Documentados

1. ❌ Lógica de negócio na View
2. ❌ Usar DTOs diretamente no State
3. ❌ Duplicar estado que pode ser computed
4. ❌ Actions sem Equatable
5. ❌ Reimplementar componentes básicos
6. ❌ NetworkService direto no Reducer (use Clients)
7. ❌ Ignorar erros (sempre trate explicitamente)
